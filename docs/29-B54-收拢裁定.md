# 29 · B-54 收拢裁定：wuhang kit 与 novel-engine 的 plan/write

> 作者问：「wuhang 和我自带的 plan、write 哪个更适配我这个项目？」
> 本文档是结论与依据。**裁定未执行**——等你确认后按第 3 节的步骤做。

## 1. 先纠正一个前提：它们不是两套对等的系统

把 wuhang 和 novel-engine 当成「两套同类流程」是不准确的。实际分层是：

| | wuhang kit | novel-engine |
|---|---|---|
| 本质 | **提示词方法论**（提问清单 + 产出模板） | **执行引擎**（状态层 + 闸门 + 契约） |
| 有无状态层 | 无（不写 state，不记指纹） | story.json / facts / judges / checkpoints，276 项测试钉着 |
| 有无闸门 | 无（审查靠提示词自查） | 机械 gates + 语义判据（B-11），exit 契约（B-14） |
| 有无锁 | 无 | 书级写锁（B-25） |
| 脚本 | 仅 2 个辅助（summarize.py / count_chinese_words.py） | 全链路 |
| 它的 SKILL.md | **已带映射表**：`1-边界→1-边界`、`2-设定→world/+characters/+constitution`、`3-大纲→outline/`、`4-正文→chapters/`、`5-审查→notes/+review/` | —— |

最后一行是关键：**wuhang 早就被适配成在 novel-engine 的目录结构上工作**。
它不是第二套状态系统，是叠在同一个书目录上的**另一套提问方式**。

## 2. 裁定：按阶段分工，不做整体二选一

**novel-engine 是唯一真相源**（状态、闸门、执行）。
wuhang 保留 **novel-engine 没有的两个前置阶段**，重叠的三个阶段停用：

| wuhang 阶段 | 裁定 | 理由 |
|---|---|---|
| 1-边界确定（样板书拆解） | **保留** | novel-engine 没有对等能力：`style-anchor`（B-48）只做**节拍校准**，不做完整的「拆一本书」 |
| 2-创意与设定（脑暴多方案） | **保留** | novel-engine 的 plan 只有**初次起草**，没有「多方案脑暴→作者挑选」这一步 |
| 3-大纲 | **停用**，改走 `novel plan` | plan 有分层确认（position→setting→outline→volume，B-40 滚动展开）+ confirm 契约；wuhang 的大纲产出不进 state，后续闸门读不到 |
| 4-正文 | **停用**，改走 `novel write` / `generate` | 收敛循环（过闸→判据→定点修订）+ 锁 + checkpoint，wuhang 都没有 |
| 5-审查 | **停用**，改走 `novel gates` + `judge` | 机械判据 + 语义判据 + 引句核对（B-11），比提示词自查严格一个量级 |

**一句话**：wuhang 负责「**想清楚**」（拆书、脑暴），novel-engine 负责「**写出来并守住质量**」。
重叠的三个阶段停用，因为它们产出不进 state——不进 state 的产出，后续的闸门、判据、
反查、完本报告**全都看不见**，等于白做。

**为什么不是反过来（以 wuhang 为主）**：novel-engine 是本项目自己的规格
（docs/novel-engine 开发文档 v0.2）的实现，带 276 项测试与硬契约；
wuhang 的脚本绑死阶段目录相对路径（项目 MEMORY 既有裁决：kit 私有，不迁入 tools/），
没有状态层，无法支持指纹绑定、回滚、反查、完本报告——这些恰恰是长篇最需要的。
