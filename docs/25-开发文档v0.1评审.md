## 二、内部逻辑矛盾

### A1 Phase 单调，与回滚、设定变更冲突
I4 和 M12.2 规定 Phase 永不回退，而 W5 要求能回滚到任意 checkpoint，L3 要求改设定后重写旧章。
如果回滚跨越了 `outline → writing`（比如回到大纲阶段的存档），就和 I4 冲突。
**改法**：I4 改为“正常流程中单调”，回滚走显式的 `rollback` 操作，写 journal，不经过 `assertTransition`。

### A2 checkpoint 只存哈希，恢复在逻辑上几乎必然被拒
M4.7 要求 checkpoint 的 `storyIndexHash` 必须等于**当前** `story.json` 的哈希才能恢复。
但需要恢复的场景恰恰是“checkpoint 之后又有写入，然后崩了”（L4 第 3 行），这时两边一定对不上。
checkpoint 只存哈希，不存快照，就没有东西可以恢复。
**改法**：checkpoint 保存 `story.json` 的完整快照（它本来就是小文件），恢复等于拷回快照；
哈希只用来检测“当前状态是否被人改过”，改过就提示，不再拒绝。
commit 与 checkpoint 之间的窗口（L4 已经点到）用“先写 checkpoint，再改指针”的两步提交来关。

### A3 幂等键取错了
M9.6 和 M12.12 用正文的 `contentHash` 当幂等键，可正文要生成之后才知道，拿它判断“是否已生成”就成了循环依赖。
**改法**：幂等键 = hash(蓝图 + PromptBundle + 模型名 + 段号)，也就是输入哈希；`contentHash` 只用作内容指纹。

### A4 M5.5“同一章抽两次结果一致”做不到
LLM 输出不确定，同一章抽两次不可能保证一致。
**改法**：状态库里每条事实都带 `sourceChapter`；重新抽取某章时，先撤掉该章之前贡献的全部事实再合并。
这样幂等性由“按章替换”来保证，不依赖模型每次输出一致。

### A5 Extract 什么时候跑，两处写法不一样
M5.8 写 Extract“与 Gates 并行”，M12.4 写 `Gates ∥ Review → 判定 → Extract`，是串行在判定之后。
**建议**采用 M12.4：没通过的稿抽出来也会被丢掉，属于白花钱。

### A6 Gates 与 Reviewer 的分工被 V3 打破
M11.5 要求两者“不检同一项”，节奏和钩子属于 Reviewer 的维度；
V3 却写“每章 ≥1 小爽点、章末有钩子：**Gates 强制，缺则 fail**”。
docs/23 已经实测：钩子按字面判定，16/19 是假红。**钩子必须归 Reviewer（语义层）**，V3 要改。

### A7 Reviewer 看不到前情，“吃书”就没人管了
M11.7 规定不给评审喂全书摘要，这是为了防止它越界去评全书基调，出发点合理；
但这样一来，跨章一致性（上一章受了重伤，这章生龙活虎）就只剩字面 Gates 能查，而字面 Gates 查不出语义矛盾。
**改法**：单独设一个“连续性判据”，只喂本章正文 + 出场角色**截至上一章**的状态 + 上一章摘要，
专门回答“和已发生的事实有没有冲突”。它和审美评审是两个 prompt。

### A8 Arbiter 的置信度不可信
M13.4 用 `confidence < 0.6` 转人工，但模型自己报的置信度没有经过校准，0.6 这个阈值没有实际意义；
M13.6 的“同输入同输出”在温度 0 下也无法保证。
**改法**：改用自洽性采样（同一题问 3 次，结果不一致就转人工），或者干脆把这四类裁定默认交给人，
自动裁定只作为可选项。

### A9 M14 压缩管线套错了模型
L1“清理旧工具返回”、L3“替换旧消息”是**多轮对话 agent** 的压缩思路；
而本系统的 `buildPrompt` 每次都是按预算表从零组装的无状态 prompt，根本不存在“旧消息”。
真正需要的只是 M6.2 的按优先级裁剪。**建议删掉 M14，把“恢复包”这层意思并进 M6**（第 3、4、5 块不裁剪）。

### A10 重写和修订不分
M11.8、M12.6 触发的是“重写该章”，但 M11.4 已经给出了带原文定位的 `{quote, problem, fix}`，
定点修订比整章重写更便宜，也更不容易改出新问题。仓库里已经有 `revise` 模式。
**改法**：先按问题修订，修订仍不通过再整章重写，并分别计数。

## 五、没考虑到的点

1. **成本和预算**（X1 被引用但不存在）：单章 token 上限、全书预算、到上限就停；要记录每章实际花费。
2. **质量怎么衡量**：V3 全是“零硬伤”这类门槛，没有“写得好不好”的度量。
   需要一个**固定评测集**（例如 10 章的蓝图 + 人工标注的好稿），每次改 prompt、规则或模型都跑一遍对比。
   同时把人工改稿量（feedback diff 行数）作为北极星指标。
3. **人和引擎同时改同一章**：作者在编辑器里改正文时引擎在跑。M4.8 的锁只防 CLI 和 server 互相冲突，防不了编辑器。
   需要 commit 前再核一次 contentHash。
4. **Windows 上的文件锁**：进程崩溃后会留下死锁文件。锁文件要写 pid + 时间戳，并能判定过期。
5. **中文 token 估算**：`字符数 × 1.5` 对现在主流的分词器明显高估（通常每个中文字 0.6–1 个 token），会裁掉过多上下文。
   **改法**：用 LLM 返回的 usage 校准系数，并写进配置。
6. **分段写作是不是必要**：现在的模型一次能写 3–4 千字。分段会引入段与段之间的接缝，M9.7 的“去重复句式”也没有定义怎么做。
   **建议**：默认整章一次生成，分段只作为兜底。
7. **长程检索怎么实现**：M6.6“四维反查 top-k”没写算法（向量检索？结构化查询？）。
   **建议**先做基于 story.json 的结构化查询（按角色、伏笔 id、地点过滤），效果不够再上向量检索。
8. **日志安全和磁盘占用**：`state/llm/<ts>.json` 要确保不写入 API key；每章都存 checkpoint + 20 份备份 + 全量 prompt，要有清理策略。
9. **prompt 注入**：M6.10 包成 data 区是对的，但参考书、拆书素材属于外部文本，还应该过滤掉“忽略以上指令”这类内容。
10. **平台合规**：敏感词、平台审核规则（番茄 / 起点）是发布前的硬门槛，完全没有涉及。
11. **版本管理**：W5 自己实现 diff 和回滚成本很高。书目录本身就可以是一个 git 仓库，每次 commit 对应一次 git commit，diff、回滚、审计都能直接用 git。
12. **多书和多卷的文件命名**：`ch-XXXX` 这样全局编号，还是每卷单独编号？和现有 `outline/ch-NN.md`（两位数）不一致，超过 99 章就会出问题。
13. **测试策略**：不变量说“也是回归测试”，但 LLM 模块怎么测没写。需要一个假的 LLM（按录制好的 `state/llm/*.json` 回放），让 Engine 能离线、确定性地测试。

## 六、值得保留的好设计（v0.2 不要丢）

- 事实层以文件为准，JSON 只做索引（仓库已落地）
- M8.4、M8.9、L6：只滚动展开下一卷，先修指南针再展开下一卷
- 蓝图的 `payoffLevel`、`hookType`、`pacing` 必填，不给默认值
- M5.4 抽取结果做防幻觉校验（但只按字面命中太脆，建议再加别名表）
- 角色信息边界 `knows` / `ignores`
- M7.5 遇到 4xx 不重试，M7.10 熔断（仓库已有）
- M12.6 超过上限就停下等人，不静默放行
- L3 设定变更：影响分析 → 人工圈定 → 顺序重写，不做全局自动重写
- W 部分：前端不持有业务状态，流式文本不放进 useState
