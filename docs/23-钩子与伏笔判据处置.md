## 1. `state --set`：保留入口，剥掉越界部分

**改法**：新增 `packages/core/src/state.ts` 的 `stripGateStatus(state)`，`novel state --set`
在 `writeState` 前调用它；被摘掉的章数如实报到 stderr 与 stdout。

**为什么是「剥掉」而不是「拒绝」**：拒绝会让只想改一个数据字段（`story_time`／`rank`）
的正常调用方连坐；剥掉只损失它本就不该提供的能力。

**实测（探针书，含真实 mtime 的伪造绿）**：

| 步骤 | 结果 |
|---|---|
| `novel state --set` 喂 `{worst:"clean", checkedMtimeMs:<真实 mtime>}` | stdout `gateStatusRemoved: 1`；落盘后 `gateStatus: null` |
| **反证**：绕过 `--set`，直接把同一份 JSON 写进 `state/story.json` | 读回来仍是 `{"worst":"clean",...}` ——**存活**，会被显示成「已检通过」 |

反证这一步是必要的：它证明这枚伪造的绿**不是空转夹具**，而是真能骗过过期清扫的攻击；
否则「净化生效」可能只是「夹具本来就没用」。

**回归网**：`packages/core/test/gate-invariants.test.ts` 新增 2 项
（`stripGateStatus` 不连坐数据字段且不改写入参；伪造的绿经 `writeState` 落盘后读回来仍是待检）。

> ⚠️ **已知缺口（如实记录）**：这两项测试验的是 `stripGateStatus` **函数**，
> 不是「CLI 真的调用了它」。本仓没有 CLI 级测试基建（`apps/cli` 无 `test` 脚本，
> 且引入它意味着测试依赖 `dist` 构建产物）。当前靠探针实测覆盖，见上表。
> 这正是本仓反复踩的「守卫在但零调用者」那一类风险，故在此显式记下。

## 2. `hook_check`：删 Python 那份，接上 `hooks.ts`

**删除**（Python 侧）：
- `gates/consistency_check.py`：`_hook_check` 函数（原 194–223）、调用点、
  `print_checks` 的机检项行、未生效节的 `hook_check` 分支；
- `gates/kit.py`：`config_problems` 里 `hook_check` 的类型校验。

**新增**（TS 侧）：`apps/cli/src/commands/hooks.ts` —— `novel hooks --book <书根> [--all]`。
判据不重写，只调 `readHookSpecs` + `auditHooks`；`paths.outline` 复用 `readiness.ts` 的
`declaredOutlinePath`（改为导出，不另写读取器）。

**守住 `docs/ne-架构与契约.md §7.2` 的三条纪律**：只出只读报告、**永不设非 0 退出码**、
红灯必带 `tail`（实际比对的末段）供人工复核。

**实测（真书《高武》）**：`specs 60 / unwritten 26 / checked 19 / skipped 15 / failed 16`。

**这 16 条红灯本身即是对 §7.2 纪律的实证**——其中至少两例是 `hooks.ts` 注释里
白纸黑字记过的已知假红：

| 章 | 细纲标的 | 正文实际写的 |
|---|---|---|
| ch-11 | 「这台仪器前天刚校准。除非……它读的压根不是你现在这个数」 | 「这台仪器前天刚**由省局技术处做过深度校准**……除非……它今天读出来的，压根就不是你现在真正的数」 |
| ch-21 | 「我要是进了正赛」 | 「我要是**真打进**了正赛」 |

钩子留得比细纲还好，词面却对不上。**结论：这条判据不能升格为拦截级闸门**——
本轮把它做成只读报告是对的，不是保守。

**数字对账**：报告里 `specs − unwritten = checked + skipped`（60−26=34=19+15），
避免读的人拿 specs 去减而算不平（与 F12 章数对账同一条道理）。

**废弃键的可见性**：`checks.hook_check` 若仍留在 book.json 里，现在**不会被任何东西读取**。
`--list-checks` 的「未生效机检项」节会点名它。
**刻意没做成 `config_problems`**——那会 `sys.exit(2)`，而两本真书都还带着 `hook_check: null`，
报成结构错误会直接把书锁死。**废弃 ≠ 配置非法。**

## 3. `foreshadow_check`：开开关之后，才发现真正卡的不是开关

**试跑第一步就撞上更隐蔽的失效**：两本真书打开开关后 **0 findings**，
看着像「查了没问题」。追下去发现是**判据与真实数据格式不符 → 零输入**：

| 书 | 伏笔表表头 | 埋设列的值 |
|---|---|---|
| 高武 | `\| 伏笔 \| 埋设 \| 半引爆 \| 状态 \|` | `6（首金）/ 23（闪回）` |
| 仙侠 | `\| 伏笔内容 \| 埋设位置 \| 预期收回 \| 状态 \| 备注 \|` | `第 1 / 16 / 38 章` |

旧实现写死「**第 3 列**、且必须是**裸整数**」（`fid, name, plant = cells[0], cells[1], cells[2]`），
两本书**一行都解析不出来**，且静默返回 0 条。**两本真书的表格式互不相同，
本仓也没有任何伏笔表模板**——即不存在一份被实现的 schema。

**改了两处**：

1. **判据**（`_foreshadow_rows`）：按表头里含「埋设」的那一列定位（不写死列号，兼容
   「埋设」与「埋设位置」）；从该列**宽松抽取**所有数字（认 `第80章`／`6（首金）`／
   `33–34`／`1 / 16 / 38`）。仍是词面口径，不判语义。
2. **静默**（`print_checks`）：解析不出任何行时，**机检项行与未生效节都必须出声**。

**实测（修复后）**：

| 对象 | 解析到的伏笔 | findings |
|---|---|---|
| 高武 | 16 条 | 0 |
| 仙侠 | 8 条 | 0 |

现在这个 0 是「真的查了且没问题」——因为**解析条数被写进了 `--list-checks` 的机检项行**
（「本次解析到 16 条伏笔」），0 条输入与 0 条发现不再同形。

**突变验证（探针书）**：造一张两行伏笔表，ch-01 故意不写「青铜钥匙」、ch-02 写了「玉佩」——

| 探针 | 预期 | 实测 |
|---|---|---|
| A：正常表 | ch-01 红、ch-02 不红 | ✅ 恰好 1 条红，`detail=青铜钥匙的下落` |
| B：表头无「埋设」列 | 0 findings **但必须出声** | ✅ 机检项行带 `⚠️ 当前解析不出任何伏笔`；未生效节列为「已启用但**恒不生效**」 |

探针 A 证明判据有牙齿（不是恒绿），探针 B 证明静默已被堵死。

## 5. 给作者的一条判据使用提醒

`foreshadow_check` 的精度**取决于「伏笔」列填什么**：

- 填**可能出现在正文里的线索词**（如「公函」「混元」「玉佩」）→ 判据可用；
- 填**叙述性描述**（如仙侠的「写功法的那个人是药修（那八个字为什么写得理所当然）」）
  → 二元组里只有零星几个能命中，容易假红。

同理，仙侠的伏笔表自己写着「**埋得越轻越好，不许加任何提示性描写**」——
那条纪律与词面口径天然冲突。**建议：该书的 `foreshadow_check` 视情况关闭，
或把「伏笔」列改写成线索词口径。**
