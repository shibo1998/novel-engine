## P0 · 质量判据（产出质量的核心短板）

### P0-1 语义判据层：LLM 审稿 gate
- **问题 [已证实]**：`hooks.ts` 词面锚词校验在真书《高武》上 `checked 19 / failed 16`，
  多数为「细纲标意图、正文写变体」的假红（docs/23 §2）。词面匹配到顶，只能降级为只读线索。
  结果是：门禁保证了「绿不是伪造的」，但「绿」本身不代表写得好。
- **改法**：
  1. `packages/core/src/judge.ts`：`judgeChapter(bundle) → JudgeResult`，
     调 `callLLM`，强制 JSON 输出 `{criterion, verdict: pass|fail|unsure, evidence: 原文引句, reason}`。
  2. 判据清单（首批）：章末钩子兑现、细纲要点覆盖、伏笔埋设/回收、角色口吻与设定漂移、战力/数值一致。
  3. 证据引句必须能在正文中 `includes` 命中，命不中 → 该条降为 `unsure`（防幻觉）。
  4. 结果写入 gateStatus，**同样绑 `checkedMtimeMs`**；词面 `hooks` 保留为廉价预筛。
  5. 判据 prompt 放 `content/judges/*.md`，在 book.json 显式声明（沿用 rules 的显式声明纪律）。
- **验收**：对《高武》已写章跑一遍，人工抽查 16 条原红灯，假红率 < 20%；
  `unsure` 不计入 clean，也不计入拦截。
- **工作量**：2–3 天。

### P0-2 收敛循环用上语义判据
- **问题 [已证实]**：`convergeChapter` 的 revise 只由 Python 检查器 findings 驱动。
- **改法**：revise prompt 注入 P0-1 的 `fail` 条目（含证据句与理由）；上限轮数不变（3）。
- **验收**：一章从 draft 到 clean 的日志中能看到语义条目被修复。
- **工作量**：0.5 天（依赖 P0-1）。

## P1 · 系统边界与冗余

### P1-1 三套同类系统并存
- **问题 [已证实]**：本机同时生效
  - 本仓 `novel-engine`；
  - `webnovel-writer` 插件（SessionStart 钩子在本仓报 `missing .webnovel/state.json`，属空转）；
  - 全局 `novel-writing` skill + `STORY_RULES.md`。
  三套各有状态文件与审查逻辑，规则可能互相冲突。
- **改法**：
  1. 定 novel-engine 为唯一内核。
  2. 从插件移植有价值的两件：context-agent 的「写前任务书」→ `buildPrompt` 前置步骤；
     data-agent 的「正文抽事实」→ `summaries` 的事实表字段。
  3. 在本仓 `.claude/settings.json` 禁用插件钩子，或整体停用插件。
  4. `STORY_RULES.md` 中与 `content/rules` 重复的条目合并，保留一处真相源。
- **验收**：本仓会话启动无 webnovel 提示；规则只有一处定义。
- **工作量**：1–2 天。

### P1-2 清理 `content/` 无关素材
- **问题 [已证实]**：
  - `content/skills/oc-kaleidos` 与 `oc-kosmos` 逐文件近乎重复（角色扮演流水线，与小说引擎无关）；
  - `content/skills/weekly-meme-report`、`docs/legacy-SKILL.md`（441 行）等无关或过期资产；
  - `content/skills/trope-retrieval/docs/tropes_library.md`（2011 行）是否被引用 **[待核]**。
- **改法**：先产出「引用清单」（grep 每个目录是否被代码/book.json/文档引用），
  未引用的移入独立 archive 仓或删除。**删除前列清单给作者确认。**
- **验收**：`content/` 下每个目录都能指出一个引用方。
- **工作量**：0.5 天。

### P1-3 TS / Python 双语言
- **问题 [已证实]**：检查器在 `gates/*.py`（`consistency_check.py` 1052 行、`kit.py` 987 行），
  子进程调用；已发生过 hook_check「两份实现都不生效」（docs/22、docs/23）。
- **改法**：
  1. 冻结 Python gates：只修 bug，不加判据。
  2. 新判据一律 TS（P0-1 即首例）。
  3. 按调用频率逐个迁移 `consistency_check` 的子检查到 core，每迁一个删一个。
- **验收**：每次迁移附对照测试（同输入 Python 与 TS 输出一致）。
- **工作量**：持续进行，每项 0.5–1 天。

## P2 · 测试与验证基建

### P2-1 CLI 级测试缺失
- **问题 [已证实]**：`apps/cli` 无 `test` 脚本；docs/23 自承 `stripGateStatus`
  只测了函数，未测「CLI 真的调用它」——即本仓反复踩的「守卫在但零调用者」。
- **改法**：`apps/cli/test/*.test.ts`，build 后用子进程跑 `dist/index.js`，
  对临时书目录做冒烟：`init → state --set(伪造绿) → 读回 gateStatus=null`、
  `hooks` 退出码恒 0、`preflight` 未就绪非 0。
- **验收**：CI/本地 `pnpm -r test` 覆盖上述链路。
- **工作量**：1 天。

### P2-2 Python gates 无回归测试
- **问题 [已证实]**：本机 `python -m pytest` 报 `No module named pytest`。
- **改法**：加 `gates/requirements-dev.txt`（pytest），`gates/tests/` 放 md 固件 + 期望 JSON。
- **验收**：每个检查器至少一正一反两例。
- **工作量**：1 天。

### P2-3 「守卫零调用者」静态检查
- **问题**：多次出现函数在、没人调（docs/22、23）。
- **改法**：一个脚本列出 core 导出但在 apps/ 无引用的函数，纳入 test。
- **工作量**：0.5 天。

## P3 · 闭环与度量

### P3-1 feedback 候选无采纳路径
- **问题 [已证实]**：`recordFeedback` 产出 `rules/_candidates/`，但无「采纳进生效规则」命令。
- **改法**：`novel rules adopt --book <书根> --candidate <id>`：
  移动到 `rules/`、写入 book.json 声明、在 feedback.jsonl 追加采纳记录。
- **工作量**：0.5 天。

### P3-2 缺北极星指标
- **问题**：近 50 条提交以流程完整性为主，产出侧无量化反馈。
- **改法**：`novel stats --book`：每章 revise 轮数、首轮/末轮 findings 数、
  人工改稿 diff 行数（取自 feedback.jsonl）、语义判据通过率。
- **验收**：在真书上跑 20 章得到基线，之后每次改 prompt/规则对比基线。
- **工作量**：1 天。
